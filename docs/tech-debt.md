## 닫힌 부채 (경위 보존 — 2026-07-29 이전)

### 9. ✅ **해소** — sold→on_sale 재오픈 DB 미차단 (마이그 `0015`의 부수효과, 2026-07-21 코드리뷰가 연결)
- **위치:** `supabase/migrations/0002_listings.sql` → `0015_listings_update_not_sold.sql`
- **내용(당시):** `listings_update_own` RLS는 소유권만 보고 status 전이 방향을 강제하지 않음. 본인 sold 매물을 `update status='on_sale'`로 재오픈하는 것이 DB 차원에서 가능(당시 UI엔 재오픈 경로가 없어 무해).
- **해소:** `0015`가 `using`에 `status <> 'sold'`를 넣으면서 **sold 행은 UPDATE 대상으로 선택 자체가 안 된다** — 무엇으로 바꾸든(`on_sale` 포함) 0행이다. 원래 적어둔 해소안(BEFORE UPDATE 트리거)보다 단순하게 같은 결과가 났다.
- 📌 **증거는 이미 손에 있었는데 항목과 연결되지 않았다.** Story 9.7이 `0015` 원격 검증 중 테스트가 매물 하나를 sold로 바꿨다가 **판매자 경로로 되돌리지 못한 것**(0행)을 스토리에 적었으면서(`9-7-…md:432`), 그것이 #9의 red-green이라는 것은 알아채지 못했다. 코드리뷰(2026-07-21)가 이었다. **닫을 수 있는 항목이 열린 채 남는 것도 대장의 실패다**(B8 — 안 닫으면 "안 한 것"과 "했는지 모르는 것"이 구별되지 않는다).
- ⚠️ **대가가 있다 — `#91`로 등재했다.** 재오픈이 막히면서 오조작으로 sold가 된 매물을 **어떤 롤로도 되돌릴 수 없다**(관리자 UPDATE 정책 없음 · `service_role` 금지).

### 44. ✅ 버킷이 이미 존재하면 비공개·5MB·MIME 3대 상한이 조용히 무효 (9.1 리뷰 이월 → 9.0에서 해소, 코드리뷰 2026-07-19에 재수정)
- **위치:** `supabase/migrations/0012_listing_images.sql:176-184` (`on conflict (id) do nothing`)
- **내용:** 누군가 `listing-images` 버킷을 `public=true`·상한 없이 먼저 만들어 뒀다면 `INSERT 0 0`으로 통과하고 **ADR-IMG-01의 비공개 전제 + 5MB + 저장형 XSS를 막는 MIME 3종이 전부 무력화된 채 마이그는 초록**이다. 도커 실측 확인. `do nothing`은 "재적용 안전"이 아니라 **"에러 없음"만** 보장한다 — 이 대장이 #27에서 스스로 경고한 `"에러 없음"으로 갈음 금지`와 같은 함정.
- **오늘 무해한 이유:** 현재 원격 버킷은 `0012`가 만든 것이라 값이 정확하다(델타 0).
- **트리거:** 새 Supabase 프로젝트·재해 복구·누군가 대시보드에서 버킷을 먼저 만드는 경우.
- **해소:** `do update set public=excluded.public, file_size_limit=excluded.file_size_limit, allowed_mime_types=excluded.allowed_mime_types`.
- **⚠️ 함께 볼 것:** 5MB·MIME를 실제로 강제하는 건 Postgres가 아니라 **Storage API 서버**다. 게이트 스텁은 값을 저장만 하는 평범한 테이블이라 **이 둘을 전혀 증명하지 못한다** — `conventions.md §10`의 "3개 상한은 전부 DB에 박는다"는 이 축에서 사실보다 강하다.
- **⚠️ 1차 해소 시도(Story 9.0, 2026-07-19)는 구멍을 옮겼을 뿐이었다 — 코드리뷰에서 뒤집힘.** 당시 `0014`는 `update storage.buckets set ... where id='listing-images'`(bare UPDATE)로 고치고 "UPDATE는 그 구멍이 없다"고 선언했다. **사실이 아니다: UPDATE는 대상 행이 *없으면* 0행에 적중하고도 성공한다.** 즉 "이미 있으면 무효"가 **"없으면 무효"**로 바뀐 것뿐인데(fresh DB·재해복구·대시보드에서 버킷이 지워진 경우) 이 항목은 해소로 선언됐다. 같은 실패 유형(*"에러 없음"을 "정상"으로 갈음*)을 이 대장이 #27에서 이미 경고했는데 그 경고를 피하려던 수정이 다시 밟았다.
- **✅ 해소 (코드리뷰 2026-07-19 — `0014_listing_images_public_bucket.sql` in-place 재수정):** **`insert ... on conflict (id) do update set public=excluded.public, file_size_limit=excluded.file_size_limit, allowed_mime_types=excluded.allowed_mime_types`.** 없으면 만들고 있으면 덮어쓰므로 두 방향 구멍이 다 닫힌다(이 항목이 원래 제시했던 해소안 그대로다). §9.3 **(a) 자율 처리** — 멱등 가드 추가만이고 **원격 실측 델타 0**: 조회 결과 `public=true` · `file_size_limit=5242880` · `allowed_mime_types={image/jpeg,image/png,image/webp}`로 이미 일치해 재적용해도 상태 변화가 없다. 따라잡기 패치(`0014b`) 불필요.
- **⚠️ 여전히 유효한 한계:** 5MB·MIME를 **집행**하는 주체는 Postgres가 아니라 **Storage API 서버**이고, 마이그레이션 게이트의 스텁은 값을 저장만 하는 평범한 테이블이라 **이 둘을 전혀 증명하지 못한다.** 이 마이그가 고친 것은 "값이 안 들어가는 것"이지 "값이 집행되는지"가 아니다. `conventions.md §10`의 "3개 상한은 전부 DB에 박는다"는 이 축에서 사실보다 강하다.

### 57. ✅ **해소** — WebP→JPEG 폴백 경로가 테스트·실측 0건이었고, **실측해보니 폴백이 아예 안 탔다** (Story 9.4 Task 0, 2026-07-19)

- **트리거:** 구형 Safari 등에서 판매자가 사진을 올릴 때. 실패하면 조용히 규격 밖 파일이 저장된다.

- **✎ 2026-07-19 코드리뷰 2차 — 전제 자체가 의심스럽다는 지적이 추가됐다.** 캔버스 사양상 `toBlob`은 **미지원 MIME에 `null`이 아니라 PNG를 돌려준다.** 사실이라면 WebP 미지원 브라우저에서 **폴백 분기가 아예 안 타고**, `extensionFor`가 `.jpg`로 이름 붙이는데 실제 내용은 `image/png`가 되어 확장자↔내용이 어긋난다(1600px PNG는 문서에 적힌 WebP 용량을 쉽게 넘어 AC4 보장도 깨진다). **측정 전엔 어느 쪽도 단정하지 않는다** — 아래 예약 작업에서 `toBlob` 주입과 함께 **이 동작부터 실측**한다.
- **📅 예약: 9.4 착수 전 단독 작업.** 추측으로 고치지 않는다 — `toBlob`을 주입 가능하게 바꿔 폴백 분기를 **먼저 측정**한 뒤 판단한다.

- **✅ 2026-07-19 실측 결과 — 코드리뷰 2차의 의심이 맞았다.** HeadlessChrome 151(로컬 chromium)에서 `canvas.toBlob`을 직접 태워 관찰:

  | 요청 MIME | `blob.type` | 앞 4바이트 |
  |---|---|---|
  | `image/webp` | `image/webp` | `52 49 46 46` (RIFF) |
  | `image/tiff`·`image/avif`·엉터리 문자열 | **`image/png`** | **`89 50 4e 47` (PNG)** |

  즉 미지원 MIME에 `null`이 오지 않는다 → **`if (blob) return blob;` 폴백은 한 번도 실행될 수 없었다.** 결과적으로 WebP 미지원 브라우저에서는 PNG가 그대로 저장되고, `extensionFor`가 `.jpg` 이름을 붙여 **확장자와 내용이 어긋났다.**
  용량 실측(1600×1067 사진형 이미지): **WebP 553KB · JPEG 503KB · PNG 4,827KB(약 9배)** — 버킷 5MB 상한에 닿고 AC4 저장본 규격 보장이 깨진다.
- **해소 방식:** `encodeWithFallback(toBlob)`을 분리해 **`toBlob`을 주입 가능**하게 했고, 판정 기준을 `blob !== null`이 아니라 **`blob.type === 요청한 타입`**으로 바꿨다(null을 주는 브라우저와 PNG를 주는 브라우저를 **둘 다** 잡는다). 둘 다 실패하면 규격 밖 파일을 조용히 저장하지 않고 throw한다. 회귀는 `resize.test.ts`의 5건으로 고정했고 **옛 코드로 되돌려 red 2건을 확인한 뒤 green으로 복구**했다(B4).
- **이 검사가 안 보는 것:** "구형 Safari가 정말 이렇게 동작하는가"는 증명되지 않았다 — 고정한 것은 *"요청한 타입이 안 나오면 JPEG로 간다"*는 우리 쪽 규칙이다.
