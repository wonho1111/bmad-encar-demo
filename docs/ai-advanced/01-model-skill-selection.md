# 01. 모델·스킬 탐색 및 선정 근거

> AI 고도화 과제를 시작하기 전에 "무슨 모델·무슨 스킬을 왜 골랐는지"를 남겨두는 문서입니다.
> 아래 수치는 전부 실측한 값이고, 과장 없이 그대로 적었습니다(측정 환경은 각 절에 표기).

---

## 1. 과제 맥락

**현재(as-is)**: 이 프로젝트의 AI 기능(3장에서 설명한 LangGraph 검색 등)은 전부 Gemini API 호출로 동작합니다. 즉 "AI가 답을 만드는" 부분을 전부 외부 API에 맡기고 있습니다.

**할 일(to-do)**: 이번 과제는 두 갈래입니다.

1. **허깅페이스(Hugging Face, AI 모델을 올리고 받는 공개 저장소) 오픈모델 탐색·검증 후 서비스 런타임 부품으로 장착.** 즉 API를 부르는 대신, 모델을 직접 내려받아 우리 서버 안에서 돌리는 부분을 만드는 것.
2. **skills.sh 스킬 조합으로 개발 프로세스 구축.** 스킬(skill)은 Claude Code가 특정 작업을 할 때 참고하는 지침 묶음입니다 — 이번엔 그걸 찾아 설치하는 과정 자체가 과제의 일부.

메인으로 만들 기능은 두 가지입니다.

- **매물 추천 고도화**: 에이전트(스스로 도구를 골라 호출하는 AI) + RAG(문서를 찾아 그 내용을 근거로 답하는 방식) + 리랭커(1차로 찾은 후보를 다시 정밀하게 순위 매기는 모델).
- **실매물 시세 진단**: 유사 매물의 SQL 통계 + TabPFN 적정가 예측(4장) + 산점도 시각화.

## 2. 스킬 탐색·선정 (skills.sh, `/find-skills` 절차)

### 탐색 방법

`find-skills` 스킬의 지침대로 진행했습니다. 이 지침은 "리더보드(설치 많은 순 목록) 확인 → `npx skills find`로 키워드 검색 → 설치 수·출처(공식 조직 계정인지) 검증" 순서를 따르라고 정해두고 있어서, 임의로 다른 방법을 만들지 않고 그대로 따랐습니다. 이번 과제에 관련된 키워드로 20여 개를 검색했습니다(예: rag, reranker, tabular, forecast, chart, statistics, langgraph, fastapi, postgres 등).

### 발견: 런타임 부품형 스킬은 마켓에 사실상 없다

스킬은 어디까지나 "Claude Code가 코드를 작성·운영할 때 참고하는 지침서"이지, 서비스가 요청마다 실행하는 부품이 아닙니다. 그런데 이번 과제의 핵심(통계 계산, 시세 예측, 차트 생성을 **서비스가 직접 수행**하는 부분)을 스킬로 대신할 수 있는지도 확인해봤습니다.

결과: 통계·시세·차트 생성을 직접 수행하는 스킬은 마켓에 거의 없었습니다. 후보로 나온 것도 quickchart류 스킬 몇 개뿐이었고 설치 수가 3~277 사이로, 이 프로젝트에서 신뢰하고 쓰기엔 기준 미달이었습니다(다른 채택 스킬들이 대부분 1천~수십만 설치인 것과 비교하면 격차가 큽니다).

→ **결론**: 런타임에서 실제로 계산·예측을 수행하는 부품은 스킬이 아니라 허깅페이스 모델 영역이라는 결론을 내렸습니다. 스킬은 "그 모델을 어떻게 다루는지"를 알려주는 역할(1절의 hf-cli, train-sentence-transformers처럼)로 쓰고, 실제 계산은 3~4장에서 다루는 모델이 담당합니다.

### 선정한 스킬 6종

전부 프로젝트 스코프로 설치했습니다(커밋 `9ed1ca1`). 괄호 안은 설치 수와 출처, 그 아래 줄은 이번 과제에서 어느 단계에 쓰는지입니다.

| 스킬 | 설치 수 · 출처 | 쓰는 단계 |
|---|---|---|
| `hf-cli` | 2.4K · 허깅페이스 공식 | 모델 다운로드·캐시 관리(리랭커·TabPFN 가중치를 받아올 때) |
| `train-sentence-transformers` | 1.1K · 허깅페이스 공식 | 리랭커(CrossEncoder) 사용법·필요 시 파인튜닝 참고 |
| `langchain-rag` | 13.8K · LangChain 공식 | RAG 파이프라인(문서 분할·임베딩·벡터 검색) 작성 시 참고 |
| `langgraph-python-quickstart` | 1.8K · LangChain 공식 | 매물 추천 에이전트의 그래프(노드·엣지) 구조 작성 시 참고 |
| `supabase-postgres-best-practices` | 375.9K · Supabase 공식 | 유사 매물 SQL 통계 쿼리·인덱스 작성 시 참고 |
| `fastapi` | 8.5K · FastAPI 공식 | 새 엔드포인트(리랭커·시세진단) 작성 시 참고 |

### 특이사항: 마켓 목록과 실물이 다른 사례

`langgraph-docs`(설치 수 4.5K)는 skills.sh 마켓 목록에는 올라 있지만, 실제로 설치를 시도하면 원본 레포에서 이미 제거돼 있어 설치가 되지 않았습니다. 마켓 목록이 실물과 어긋난 경우로, 대신 같은 LangChain 공식 계정의 `langgraph-python-quickstart`로 대체했습니다. (마켓의 설치 수·목록은 실시간으로 원본과 동기화되지 않을 수 있다는 뜻이라, 설치 직전에 한 번 더 확인하는 습관이 필요합니다.)

## 3. HF 리랭커 선정

> 실측: 2026-08-29, 노트북(RAM 6GB, CPU만 사용). **최종 판정은 아님** — 데스크톱(16GB RAM + GTX 1060)에서 재측정한 뒤 확정합니다. 여기 적은 수치는 어디까지나 "품질 비교"용이고, 지연(속도) 수치는 노트북 CPU 기준이라 실제 서비스 배치와는 다릅니다.

### 후보

- **BAAI/bge-reranker-v2-m3**: Apache-2.0 라이선스(상업적 이용 자유), 0.6B(6억 파라미터), 월 다운로드 1,737만.
- **dragonkue/bge-reranker-v2-m3-ko**: 위 모델과 동일한 구조를 한국어 데이터로 추가 학습(파인튠)한 버전.

리랭커는 "1차로 찾은 문서 후보들을, 질문과 얼마나 관련 있는지 다시 정밀하게 점수 매겨 순서를 바로잡는" 모델입니다. 한국어 서비스이니 한국어 특화판이 유리할 거라 예상하고 두 개를 직접 비교했습니다.

### 실측 방법과 결과

실제 서비스 코퍼스(문서 묶음) 24섹션에 대해 질의 8개를 놓고 각 모델이 정답 섹션을 몇 번 맞히는지 셌습니다.

- BAAI: 8개 중 6개 적중.
- ko판(dragonkue): 8개 중 5개 적중.

ko판이 떨어진 원인을 들여다보니, "가성비 좋은 중고차" 질의에서 점수가 붕괴했습니다 — 1등으로 뽑은 섹션의 점수가 0.0004로, 사실상 무관한 섹션을 1등으로 낸 것입니다. "2천만원대" 질의도 전반적으로 저점수였습니다. 즉 한국어로 파인튠은 됐지만, 그 학습에 쓰인 데이터 분포가 우리 도메인(중고차 매물·옵션 설명)과 맞지 않아서 오히려 점수 신뢰도가 떨어진 것으로 보입니다.

참고로 두 모델 다 공통으로 취약한 지점이 있었습니다 — "잔고장·수리비" 관련 질의에서는 둘 다 신뢰성 관련 섹션을 잘 못 찾았습니다. 이건 모델 선택과 무관한 문제라 별도로 추적할 항목으로 남겨둡니다.

### 지연(속도) 실측

질의 1개 × 후보 10개를 채점하는 데 걸린 시간(노트북 CPU 기준):

- BAAI: 평균 55.7초
- ko판: 평균 51.8초

CPU만으로는 이 지연이 실제 서비스에 쓰기엔 너무 큽니다(사용자가 검색 결과를 기다리는 시간으로는 부적합). 메모리는 피크 RSS(실제 점유 메모리) 기준 BAAI 1.3GB, ko판 1.1GB로 노트북에서도 여유 있게 돌아갔습니다.

### 선정 결론

**BAAI/bge-reranker-v2-m3**을 선정합니다(품질이 우위이고, ko판이 도메인 불일치로 더 불안정했기 때문).

실행 방식(어떻게 빠르게 돌릴지)은 데스크톱 재측정에서 확정할 게이트로 남겨둡니다.

1. 1안: GTX 1060(3GB VRAM)에서 CUDA(GPU 가속)로 돌리기. 0.6B 모델을 fp16(16비트 정밀도, 메모리 절반)으로 올리면 약 1.2GB로 GPU 메모리에 들어갈 수 있어 이론상 가능합니다.
2. 1안이 안 되면(예: GTX 1060의 구형 아키텍처가 최신 PyTorch CUDA를 지원 안 하는 경우) 플랜B: `gte-multilingual-reranker-base`(0.3B, 더 가벼운 모델)로 교체하거나, ONNX 양자화(모델을 더 가벼운 정밀도로 변환)를 적용하거나, 리랭킹 후보 수를 10개에서 5개로 줄여 계산량 자체를 줄입니다.

## 4. TabPFN 선정 (적정가 예측)

### 배경

TabPFN은 표 형태 데이터(엑셀 같은 행·열 데이터) 전용 파운데이션 모델(대량의 범용 데이터로 미리 학습해, 적은 데이터로도 바로 쓸 수 있게 만든 모델)입니다. 2025년 네이처(Nature)에 실린 논문("Accurate predictions on small data with a tabular foundation model")에 소개됐고, 사이킷런(scikit-learn, 파이썬 머신러닝 표준 라이브러리)과 같은 `fit`/`predict` 방식으로 씁니다 — 즉 데이터를 몇 줄 던져주면 학습(fit)하고 예측(predict)해준다는 뜻입니다.

### 후보군과 탈락 사유

- **Chronos, TimesFM**: 시계열(시간 순서가 있는 데이터, 예: 매일의 주가) 전용 모델이라, 우리가 다루는 "매물 한 대의 여러 속성(연식·주행거리·옵션 등)으로 가격 추정"이라는 표 데이터 문제와 맞지 않아 탈락.
- **sqlcoder**: 최소 요구 사양이 7B(70억 파라미터) 이상이라, 우리 하드웨어(노트북 6GB, 데스크톱 GTX 1060 3GB)로는 못 돌려서 탈락.

### 라이선스가 버전 선택을 결정했다

TabPFN은 버전에 따라 라이선스가 다릅니다.

- **v2 가중치**: Apache 2.0 + 표기 의무(서비스 화면에 "Built with PriorLabs-TabPFN" 문구를 노출해야 함).
- **v2.5 / v2.6 / v3**: 비상업 라이선스 + PriorLabs 계정 로그인 필수.

이 프로젝트는 상업적 이용을 가정한 데모라, v2 가중치를 써야 합니다. 그런데 최신 pip 패키지(버전 8.5.0)를 그냥 설치했더니 기본값이 v3 가중치를 집어서, 실행 시 브라우저 로그인 창을 요구하는 걸 실측으로 확인했습니다. 이대로면 서버가 사람 개입 없이 못 돕니다.

→ **해결**: 패키지 버전을 `tabpfn==2.2.1`로 고정했습니다. 이 버전에는 로그인을 요구하는 모듈 자체가 없어서, v2 가중치(`Prior-Labs/TabPFN-v2-reg`)를 로그인 없이 그대로 쓸 수 있습니다.

### 실측 (노트북 CPU, 합성 중고차 데이터 200행)

테스트 데이터는 "감가상각 규칙 + 5% 노이즈"로 만든 합성 데이터입니다(실제 매물 데이터가 아직 충분하지 않아 가상 데이터로 먼저 검증).

| 항목 | 수치 |
|---|---|
| 모델 로드 | 0.8초, RSS(점유 메모리) 333MB |
| 학습(fit, 160행) | 10.4초 |
| 예측(predict, 40행) | 42.0초 |
| 피크 RSS | 462MB |
| R²(설명력, 1에 가까울수록 좋음) | 0.9213 |
| MAE(평균 절대 오차) | 111만원 |

모델카드(허깅페이스의 모델 설명 페이지)에는 16GB RAM을 권장한다고 적혀 있지만, 이번 실측은 6GB 노트북에서도 여유 있게 돌아갔습니다 — 즉 권장 사양이 대용량 데이터셋 기준이고, 우리처럼 데이터 규모가 작은 경우엔 그대로 적용되지 않는다는 걸 실측으로 확인한 셈입니다.

다만 이 수치는 fit 160행 + predict 40행이라는, 다소 큰 배치를 한 번에 처리한 경우입니다. 실제 서비스에서 쓸 패턴은 "유사 매물 20~60행으로 학습 + 진단 대상 1행만 예측"이라 이보다 훨씬 가볍습니다. 최종 지연 수치는 데스크톱에서 재측정할 예정입니다.

## 5. 통합 시 알려진 제약 (실측 기록)

이번 탐색 과정에서 실제로 부딪힌 제약을 남겨둡니다. 구현 단계에서 다시 마주칠 것이므로 미리 적어둡니다.

- **의존성 충돌**: `tabpfn==2.2.1`은 `huggingface-hub<1.0`을 요구하는데, `sentence-transformers` 6.x(리랭커 쪽에서 쓰는 패키지)는 `huggingface-hub>=1.3`을 요구합니다. 같은 가상환경(venv)에 둘 다 설치하면 충돌 경고가 실제로 발생하는 걸 확인했습니다. → 통합 단계에서 (a) 두 요구사항을 모두 만족하는 호환 버전을 다시 찾거나, (b) 리랭커와 TabPFN을 서로 다른 프로세스(예: 별도 서비스)로 분리하는 방향으로 풀 예정입니다.
- **Windows MAX_PATH(260자) 제한**: 가상환경 경로가 길어지면 `pip install`이 경로 길이 제한에 걸려 실패하는 걸 겪었습니다. → `subst` 명령으로 짧은 드라이브 별칭(예: `X:`)을 만들어 우회했습니다. 같은 문제가 재현되면 이 방법을 먼저 시도하면 됩니다.
- **데스크톱 재측정 절차**: 스크래치패드의 `bench/` 스크립트를 재사용해 재측정합니다. 확인해야 할 항목에는 GTX 1060(Pascal 세대, `sm_61`)이 최신 PyTorch의 CUDA 휠(미리 컴파일된 배포판)을 지원하는지 여부도 포함됩니다 — 구형 GPU라 최신 PyTorch가 아예 이 아키텍처를 못 쓸 가능성이 있어, 리랭커 1안(GPU 가속)의 성패가 여기에 달려 있습니다.

- **DW-847**: 되묻기(clarify) 칩이 고정 템플릿이라 질의 맥락과 무관하게 항상 같은 칩이 나오는 문제. 에이전트 구조에서는 되묻기가 도구 호출의 자연스러운 일부가 되므로, 이번 과제에서 동적 되묻기로 개선합니다.
- **DW-848**: "연식은 최신일수록" 같은 정렬 요청이 벡터 유사도 순서에 묻혀 반영되지 않는 문제. 정렬 축을 명시적으로 다루는 설계가 필요합니다.
- **DW-849**: 검색 결과가 한 조건(예: 같은 연료 유형)에 쏠릴 때, 가이드 문서 지식을 근거로 다른 섹션과 조합해 결과를 다시 골라내는(되추리는) 기능이 없는 문제. 이번 과제의 에이전트 구조(검색 → 가이드 읽기 → 되추림 도구 호출)로 자연스럽게 해결하기로 판단된 항목입니다.

**진입점 확정**: 상세 페이지 버튼 + AI 채팅 자연어 두 경로로 진입합니다. 매물 목록 카드 자체는 바꾸지 않습니다.
