## 1. 무엇을 했나

"정지(suspended)"라는 관리자 조치가 **데이터 계층에서 실제로 무엇을 막는지**를 확정하고 강제했다.
착수 시점의 상태는 이랬다 — 화면에 정지 버튼이 있고 `profiles.status` 값도 바뀌지만, **그 값을 읽어
무언가를 거부하는 코드가 저장소 전체에 0건**이었다(DW-669 실측). 즉 정지된 회원은 계속 로그인해
매물을 등록·수정·삭제했다.

| 스토리 | 무엇 | 닫은 장부 | 루프 |
|---|---|---|---|
| 17-1 정지 회원 쓰기 차단 (RLS) | `0032`·`0033` — 21개 정책 + 11개 정의자 함수 전수조사 후 쓰기 경로 차단 | DW-669·717·721·674·682·782 | dev×1 review×2 · 117.8M |
| 17-2 조회수 옆문 차단 + 전수조사 강제검사 | `0034` — 정의자 함수 본문 가드 · 매니페스트 대조 검사 신설 | DW-805 · DW-803 | dev×1 review×0 · 37.4M |
| 17-3 정지 관리자 콘솔 차단 + 안내 문구 구분 | `guard.ts`·`status.ts`(신설) — 웹 4경로 안내 배선 | DW-806 · DW-804(b) | dev×1 review×2 · 119.1M |
| 17-4 정지 판매자 매물 비노출 | `0035`·`0036` — 읽기 정책 3종 좁힘 + 판정 함수 `private` 이전 | DW-804(a) | dev×1 review×2 · 66.3M |

에픽 컨텍스트 문서의 해당 항목을 폐기 표시하되 **원문은 지우지 않았다**(17-1의 코드·검사·마이그레이션
주석이 전부 그 원문을 근거로 쓰여, 지우면 그 근거들이 출처를 잃는다).

루프 보고를 옮기지 않고 **직접 다시 돌리고 직접 깼다.** 개발 세션이 **쓰지 않은 축**을 골랐다 —

## 3. 리뷰가 실제로 잡은 것 — 이 에픽의 가장 큰 수확

**정의자 함수를 `public` 스키마에 두면 Supabase(PostgREST)가 자동으로 REST RPC로 공개한다.**
`0035`가 만든 `public.is_seller_active(uuid)`는 인자를 받는 **판정 함수**라, 비로그인 상태에서
임의의 uuid를 넣어 *"이 회원이 정지됐나"* 를 물어볼 수 있는 **신탁(oracle)** 이 됐다.
`revoke all ... from public`은 이미 `anon`에 직접 준 EXECUTE를 취소하지 못해 막히지 않았다.

리뷰가 이걸 잡아 `0036`으로 함수를 `private` 스키마(Data API 노출 목록 밖)로 옮겼다.
**오케스트레이터 실측**: `POST /rest/v1/rpc/is_seller_active` → **404**, 대조군 `GET /rest/v1/listings`
→ **200**(게이트웨이 사망으로 인한 404가 아님을 함께 고정).

같은 패스에서 리뷰가 잡은 것 2건 더:
- **1차 패치가 결함을 만들었다** — `get_seller_public_summary`에 `is_seller_active` 단독 조건을 걸어
  **판매자 본인·관리자에게도 무조건 0**을 돌려줬다. "남이 볼 때만"이라는 축을 놓친 것.
- **성능 회귀** — 판정 함수에 `parallel` 절이 없어 기본값 `PARALLEL UNSAFE`가 되고, 그 함수가
  매물 조회 최핫경로 정책에 들어가면서 **`listings`를 읽는 모든 쿼리가 병렬 플랜을 못 받게** 됐다.
  ⓐ 조건을 17.4 이전으로 되돌리면 Gather 복구 ⓑ `parallel safe` 한 단어만 추가해도 복구 —
  두 방향으로 원인을 고정한 뒤 고쳤다.

> **교훈**: [[review-patches-need-their-own-pass]] 계열의 재확인 — **리뷰 패치도 리뷰 대상이다.**
> 이번엔 2회차 리뷰가 1차 패치의 결함을 실제로 잡았다(`max_review_cycles=2`가 값을 한 것).

## 5. 이 에픽이 반복 확인한 실패 모드

### 5.1 "한쪽만 보는 검사"는 재앙을 초록으로 통과시킨다

17-4의 핵심 함정은 스펙 단계에서 **미리 실측해 막았다** — `profiles`에 `anon` 대상 SELECT 정책이
**0건**이라, 읽기 정책에 인라인 서브쿼리를 쓰면 `exists`가 항상 거짓이 되어 **모든 매물이 사라진다**.
그런데 *"정지 판매자 매물이 안 보인다"* 만 단언하는 검사는 **그 상태에서도 통과한다.**

→ 처방: **정의자 함수 의무 + 모든 검사에 긍정 대조군 짝**을 스펙 요건으로 박았고,
오케스트레이터 프로브 2번이 그 대조군이 실제로 작동함을 확인했다(9건 red 중 6건이 대조군).

### 5.2 안내 문구가 **자기가 못 지킬 약속**을 한다

17-3이 만든 문구는 *"정지된 계정입니다. 매물 등록·수정·삭제와 **채팅 보내기**가 제한됩니다."* 인데,
정작 채팅 경로에는 배선이 없어 채팅 화면에선 여전히 *"메시지를 보내지 못했습니다. 잠시 후 다시
시도해주세요."*(고장으로 읽히는 문구)가 뜬다. **17-3이 매물 축에서 없앤 오인을, 17-3이 만든 문구가
채팅 축에서 새로 유도한다.** 오케스트레이터 실측: `grep -rn "getOwnStatus\|writeRejectionMessage"`
결과에 채팅 관련 파일 **0건**([[DW-813]]).

### 5.3 "막았다"와 "왜 막혔는지 알려준다"는 다른 일이다

17-3은 정지된 관리자를 `/admin`에서 튕겨내는 데 성공했지만, **왜 튕겼는지는 안 알려준다** —
사용자 입장에선 화면이 그냥 홈으로 돌아온다([[DW-814]]). 같은 축의 잔여가 사진 업로드
([[DW-815]])·관리자 콘솔 쓰기 액션([[DW-816]])에도 남았다.

### 5.4 한 층을 막으면 옆 층이 드러난다

- [[DW-819]] — 조회수는 **호출자**의 정지만 본다. 판매자가 정지돼 **아무에게도 안 보이는 매물**의
  조회수는 계속 오른다.
- [[DW-820]] — 매물은 숨겼지만 **이미 열려 있던 채팅방**에서는 구매자가 계속 말을 건다.
  DW-804(a)가 지목한 증상("영원히 답할 수 없는 판매자")이 기존 방에는 그대로다.
- [[DW-826]] — `get_seller_public_summary`가 **anon에게 임의 uuid의 계정 존재 여부와 가입일**을
  돌려준다. 3절의 신탁을 하나 막았더니 같은 성질의 함수가 하나 더 있었다.

## 6. 운영(원격) 관점에서 **아직 성립이 확인되지 않은 것**

이 에픽의 검증은 **전부 로컬**이다. 원격(운영) DB에는 `0032`~`0036` 어느 것도 적용되지 않았다.

- **[[DW-824]] — `private` 스키마 차단의 성립 조건을 원격에서 한 번도 안 쟀다.** 3절의 신탁 차단은
  *"`private`가 Data API 노출 스키마 목록 밖"* 이라는 전제 위에 서 있다. 그 목록은 Supabase
  프로젝트 설정이며, **그 계층을 도는 자동 검사가 0건**이다. 설정이 다르면 신탁이 그대로 열린다.
- 마이그레이션 원격 적용은 **사용자 승인 사항**(CLAUDE.md B3). 이 회고는 적용하지 않았다.

> **A1에 대한 솔직한 평가**: Epic 16 회고의 B3처럼 이것도 "결정만 하면 되는" 항목처럼 보이지만,
> **지난번엔 사용자가 결정까지 했는데도 이행되지 않았다.** 결정을 받는 것으로 충분하지 않다 —

> 그래서 A1은 "결정한다"가 아니라 "결정 + 자리 지정"까지가 완료 조건이다.
