# Epic 13 Context: AI 검색 RAG 고도화

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

AI 자연어 검색을 데모 수준에서 상용 수준으로 끌어올린다. 현재의 단순 라우팅(SQL 전용/벡터 전용)을 4갈래(무관·법적 질의 거절 / 광범위 질의 되묻기 / 정형 조건 Text-to-SQL / 정형+의미 혼합 하이브리드)로 확장하고, 정형 조건과 의미 유사도를 한 질의로 조합하는 하이브리드 검색, 가이드 문서 코퍼스의 실제 활용(질의 확장), 근거 없는 문서·매물이 답에 섞이지 않게 하는 거리 컷오프, 그리고 사후 관측을 위한 LangSmith 트레이싱을 도입한다. 신규 SQL 생성 경로(하이브리드)가 늘어나므로 기존 보안 안전장치(sql_guard·판매완료 매물 비노출)를 그 경로까지 확실히 확장하는 것이 이 에픽의 최우선 전제다.

## Requirements & Constraints

- 라우팅은 4갈래로 분류되어야 한다: 무관/법적 질의 → 부드러운 거절, 광범위/애매한 질의 → 조건 좁혀 되묻기, 정형 조건 질의 → Text-to-SQL, 정형+의미 혼합 질의 → SQL+벡터 하이브리드.
- 하이브리드는 단일 쿼리(구조조건 WHERE + 유사도 ORDER BY)로 조합한다(RRF 없음). 구조조건을 못 뽑으면 기존 벡터검색으로 폴백해 회귀 없이 처리한다.
- 하이브리드로 생성되는 SQL도 예외 없이 기존 SQL 검증기(sql_guard)를 통과해야 하고 판매완료(`status='on_sale'` 아님) 매물을 강제로 걸러야 한다 — 이 프로젝트의 판매완료 비노출 규칙(FR11)이 지키는 지점이 기존 3곳(행 단위 접근제어·SQL 검증기·문서 RAG 필터)에서 하이브리드 벡터 검색까지 4번째로 늘어난다. **앱 레벨 필터링은 금지하고 쿼리/DB 레벨에서만 막는다.** 이건 보안 블로커 등급 요구사항이다.
- 가이드 문서(현재 12개, 상식 기준을 담은 코퍼스)는 검색 조건/가중치로 반영되어야 하지만 답변 문장 자체는 여전히 결정론적(고정 템플릿 조립)으로 생성해야 한다 — LLM이 가이드 본문으로 자유 문장을 만들지 않는다.
- 코사인 거리가 임계값 이하일 때만 가이드 문서를 답변 근거로 채택한다(임계값은 하드코딩이 아니라 실측 질의셋으로 튜닝해 확정, 초기 후보 0.3).
- 문서 청킹은 현재 규모(page-level)에서는 도입하지 않는다(문서 20개 이상 또는 **문서당** 800토큰 이상일 때만 재검토 — 13.8 3차 리뷰 정정: "문서당" 한정어가 재컴파일에서 빠져 총량 기준으로 읽히면 이미 초과라는 반대 결론이 나온다).
- LangSmith 트레이싱은 환경변수 2개만으로 켜지는 무료 티어를 쓴다(코드 변경 없음, 평가 자동화·유료 Deployment는 도입 안 함, 월 5000 트레이스 상한).
- `/ai/search`는 로그인(JWT) 필수를 유지한다 — 비로그인 열람 허용은 매물 목록/상세에만 적용되고 AI 검색은 호출마다 Gemini 실비가 드는 "행동"이라 별개다. 이 프로젝트는 "비용이 드는 엔드포인트는 신원을 요구한다"는 원칙을 전 에픽에 걸쳐 유지하며, 하이브리드 도입으로 검색 1회당 LLM+임베딩 호출이 늘어나는 것도 같은 근거로 신원 요구를 완화할 이유가 되지 않는다.
- 되묻기(CLARIFY)는 세션 상태를 서버에 두지 않고(무상태), 사용자의 다음 메시지를 클라이언트가 이전 맥락과 이어붙여 재전송하는 방식이다. 되묻기는 최대 2~3턴까지만 허용하고, 초과하면 현재까지의 조건으로 결과를 강제 제시한다(무한 되묻기 금지).
- **거절(REJECT)은 고정 템플릿만 쓴다 — LLM 자유 재작성 금지.** 0건·거절 응답의 다양성도 문구 생성이 아니라 서버가 내려주는 구조화 사유 데이터(`narrowed_by`)를 결정론 템플릿이 조립해서 만든다. (13.8 3차 리뷰 복원: 재컴파일에서 이 제약이 Requirements에서 빠지고 문구 예시만 UX 절로 내려가, 요구사항만 읽는 다음 스토리가 0건 안내에 LLM 생성 문구를 넣어도 막을 근거가 문서에 없었다 — CLAUDE.md B8 "각주에 둔 제약도 지켜야 하는 것이면 본문으로 올린다".)
- AI 검색 입력은 서버 측에서도 500자 상한을 검증한다(클라이언트 검증만으로는 우회 가능).
- 회귀 방지를 위한 실측 기준선(baseline query set, 47개 질의 — 정본은 `api/docs/ai-ab-test-queryset.json`의 항목 수이며 이 숫자는 사본이다)을 13.1에서 심고, 이후 RAG 관련 스토리마다 재실행해 품질이 그 기준 아래로 떨어지지 않는지 확인한다.
- 검증 게이트는 모두 실측으로 통과해야 한다: G1(되묻기 과다발동 방지 — 명시조건 질의가 CLARIFY로 새면 실패), G2(회귀 — Phase B baseline 이하로 떨어지면 실패), SM-F(기존 AI 검색 시연 3종 유지), SM-G(신규 3분기 = HYBRID·CLARIFY·REJECT 각 1개 이상 실동작), CM-B(sql_guard·ai_readonly·판매완료 비노출 유지). (13.8 3차 리뷰 정정: 아래 Cross-Story Dependencies가 같은 게이트를 "신규 4갈래"로 적어 판정 범위가 문서 안에서 갈렸다 — SQL은 신규가 아니라 SM-F가 보는 기존 경로다. 다만 13.8의 라이브 스모크는 실제로 네 갈래를 전부 단언했다.)
- 라우터는 최상급·정렬 표현(예 "제일 싼", "가장 비싼")을 조건 없음이 아니라 구조조건으로 취급해야 하고, 명시 차종이 든 교체 요청("~같은 SUV로 바꿔줘")도 SQL로 라우팅되어야 한다 — 실측 결함: 이런 표현이 다른 구체조건 없이는 되묻기(CLARIFY)로 새거나, 같은 형태가 조합에 따라 SQL/CLARIFY로 갈리는 불안정이 있었다.
- 대화 초기화(RESET) 오염 검사는 "매물 0건이라 우연히 통과"하는 상태에 머물지 않아야 한다 — 실제 오염 데이터를 넣어 검사가 실패로 잡히는지까지 확인한다(설정이 존재하는 것과 실제로 걸러지는 것은 다르다).
- 멀티턴 맥락 재작성(`contextualize_query`)은 이전 조건을 이어받는 후속 질의를 원문 그대로 넘기지 않고, 조건(가격·차종·지역 등)을 접어 넣어 혼자서도 이해되는 독립 질의로 재작성해야 한다(재작성 실패 시 원 질의로 되돌리는 기존 폴백은 유지).
- 위 라우팅 케이스는 라이브 재캡처와 별개로 결정론적 단위테스트로도 고정한다 — 라우터 프롬프트가 다시 흔들리면 이 단위테스트가 먼저 잡아내야 한다.

## Technical Decisions

- sql_guard 화이트리스트는 벡터 연산자(`<=>`)·`::vector` 캐스트를 전역으로 허용하는 게 아니라 `ORDER BY embedding <=> %s::vector` 라는 정해진 모양·위치에서만 통과시킨다(위치 무관 허용은 안전하지 않음). 벡터절 자체는 LLM이 만들지 않고 코드가 붙인다 — `%s`는 질의 임베딩을 바인드 파라미터로 받고 `LIMIT k`는 코드가 정수 리터럴로 붙인다(바인드 파라미터 아님). LLM은 WHERE의 구조 조건만 생성한다.
- 하이브리드 SQL 회귀 테스트는 최소 3케이스: 정상 벡터 쿼리 통과 / OR·서브쿼리 주입 거부 / status 필터 누락 거부.
- DB 커넥션 풀의 롤 격리(`BEGIN; SET LOCAL ROLE ai_readonly; ...; COMMIT;`, 세션 레벨 SET ROLE 금지)는 Epic 8에서 이미 선행 완료된 전제이며, Epic 13은 그 위에 하이브리드를 얹는다.
- 4분기 라우팅은 `RouterDecision` Literal 타입·`_fallback_route`·`_route_decision` 세 곳이 항상 락스텝으로 갱신되어야 한다 — 하나만 빠뜨리면 새 라우트가 조용히 이전 갈래로 흡수되는 회귀가 생긴다.
- AI 응답 계약: `{ answer, listings: ListingCard[], route: 'REJECT'|'CLARIFY'|'SQL'|'HYBRID', narrowed_by?: string[], clarify?: {question, chips[]} }`. `narrowed_by`는 저장 단위(원) 그대로의 정규화 술어 배열(예 `["price<=30000000"]`)이며, 한국어 문구로의 변환은 결정론 템플릿(answer_node)이 담당한다. `clarify` 필드는 route='CLARIFY'일 때만 채워진다.
- 되묻기 상태(멀티턴 맥락)는 클라이언트가 소유하고 sessionStorage에 지속시켜 새로고침에도 살아남게 한다. **상한은 서버가 강제한다** — `api/app/graph/graph.py`의 `_CLARIFY_TURN_CAP`(=3)이 `context` 길이로 총 턴 수를 계산해 `_clarify_step`에서 막고, 초과하면 클라이언트 협조와 무관하게 `doc_rag_node`로 결과를 강제 제시한다. (13.8 3차 리뷰 정정: 이 줄은 원래 "상한도 클라이언트가 강제한다(서버가 무상태이므로)"였는데 코드와 정면으로 어긋난다 — DW-563이 정확히 "클라이언트만 세는 상한은 상한이 아니다"를 근거로 서버 강제로 옮겼고, web 클라이언트엔 턴 카운터가 없다. 무상태는 "상태를 저장하지 않는다"는 뜻이지 "판정하지 않는다"가 아니다.)
- 이 에픽은 신규 아키텍처가 아니라 기존 LangGraph 그래프 위에 노드를 추가하는 확장이다 — `interrupt()`나 체크포인터 같은 무거운 신규 인프라는 도입하지 않는다.
- 13.9는 라우팅 판정 구조 자체를 바꿀 수 있다: 현재는 "LLM 감으로 갈래를 먼저 정하고 그 다음 조건을 뽑는" 구조라 프롬프트가 다루지 않은 표현에 흔들린다. 대안은 "조건을 먼저 추출하고, 그 결과로 코드가 갈래를 결정"(추출 실패=되묻기)하는 구조로, 이미 하이브리드 노드에 부분적으로 존재하는 패턴이다. 이 스토리는 프롬프트 보강만으로 끝낼지 이 구조로 바꿀지 판단하고 근거를 기록해야 한다 — 단, 어느 쪽을 택하든 4분기 라우팅(13.2)의 인수조건과 `RouterDecision`·`_fallback_route`·`_route_decision` 3곳 락스텝 계약은 깨지 않아야 한다.

## UX & Interaction Patterns

- 거절 응답은 고정 템플릿(무상태·결정론, LLM 자유 재작성 없음)이다: "저는 중고차 찾기를 도와드리는 차장님이에요 🚗 그건 답하기 어렵지만, 원하는 차 조건을 말씀해 주시면 딱 맞는 매물을 찾아드릴게요." — 뒤에 원 조건 재제안 칩을 붙여 막다른 길처럼 느껴지지 않게 한다. **⚠️ 여기 적힌 문구는 사본이다. 정본은 `api/app/graph/guard_node.py`의 `_GUARD_ANSWER`**이며 `tests/test_demo_acceptance.py`가 그 상수를 바이트 단위로 단언한다 — 문구를 바꿀 땐 코드를 먼저 고치고 이 줄은 따라온다(13.8 3차 리뷰 추가: 같은 커밋이 `ai-demo-queries.md`에는 이 표시를 붙이면서 여기엔 표시 없이 전문을 복사해, 이 사본만 조용히 늙을 자리였다).
- 되묻기 응답의 도입 문구는 "조건을 조금만 좁혀볼게요 —" + "칩을 눌러도 되고, 직접 입력해도 돼요."로 고정한다. 되묻기 칩은 탭하면 petrol(테마 색) 채움의 "선택됨" 상태가 되고, 자유 타이핑과 동등한 입력 경로로 취급한다(칩 vs 타이핑 중 뭘 써도 같은 다음 턴으로 이어짐).
- 칩은 스타일이 다른 2종이다 — 상시 제안칩(petrol 반투명, 입력바 위 상시 노출)과 맥락 칩(되묻기·거절 전용, 탭 시 petrol 채움 "선택됨" 상태로 전환). 맥락 칩 탭은 자유 타이핑과 항상 동등한 입력 경로이며, 자유 타이핑은 칩 존재와 무관하게 항상 병존한다.
- 전체적인 AI 응대 톤은 "차장님" 페르소나(정직·따뜻·믿음직)를 유지하며 개발/스펙 용어를 노출하지 않는다.
- AI 대화는 스크린리더로 발화자(차장님/나)를 구분해 안내하고, 타이핑·스트리밍 상태는 `aria-live="polite"`로 과도한 알림 없이 전달한다.

## Cross-Story Dependencies

- 13.1(sql_guard 정비 + 회귀 기준선)이 선행되어야 13.3(하이브리드 검색)이 안전하게 SQL을 생성할 수 있다 — 13.1의 화이트리스트·강제 조건이 없으면 13.3은 보안 요구를 만족하지 못한다.
- 13.2(4분기 라우팅 골격)가 있어야 13.3(HYBRID)·13.4(CLARIFY)·13.5(REJECT) 각 갈래가 실제로 호출될 진입점이 생긴다.
- 13.6(가이드 활용)과 13.5(거절)는 둘 다 answer_node의 응답 조립 로직을 건드리므로 작업 순서에 주의한다.
- 13.8(exit-gate 검증)은 13.1~13.7 전체가 구현된 뒤에만 의미가 있는 종합 검증 스토리다 — 원본 AI 검색 시연 3종 유지, 신규 3분기(HYBRID·CLARIFY·REJECT) 각 1개 이상 동작, 회귀 기준선 이하로 떨어지지 않음, 판매완료 비노출 등 안전장치가 하이브리드/실시간 전환 후에도 유지되는지를 함께 확인한다. **G2 미통과 시 에픽을 종료할 수 없다.**
- 13.9(라우팅 안정화)는 13.8 종료 **이후에만** 착수한다 — 13.8이 사용한 기준선 파일(`api/docs/g2-baseline.json`)을 흔들지 않기 위해서다. 13.9 완료 후에는 그 기준선을 재캡처하고 13.8의 회귀 게이트를 새 기준선으로 다시 통과시켜야 한다.
- Epic 8에서 이미 만든 DB 커넥션 풀 롤 격리(AC-DB-1)와 ListingCard 응답 계약 셸(image_url·view_count·image_count 등 nullable 필드)이 이 에픽의 전제 조건이다 — 하이브리드 검색 결과 카드도 동일 ListingCard 계약을 그대로 사용한다.
