# Epic 13 Context: AI 검색 RAG 고도화

## Goal

AI 검색을 상용 수준으로 끌어올린다: 질의를 4갈래(거절/되묻기/구조형/하이브리드)로 정확히 라우팅하고, 정형 조건과 의미 조건을 한 SQL 쿼리로 조합하는 하이브리드 검색을 추가하며, 가이드 문서의 상식 지식을 검색 조건 확장에 실제로 활용하고, 근거 문서에 거리 컷오프를 적용하며, LangSmith로 라우팅·가드 차단·되묻기 발동을 관측 가능하게 만든다. 목적은 두 가지다: (1) 지금은 놓치는 혼합형·상식형 질의에 정확한 답을 주는 것, (2) 안전장치(sql_guard·ai_readonly·판매완료 비노출)를 유지한 채 품질 회귀 없이 이를 달성했음을 증명하는 것. 커넥션 풀 롤 격리(AC-DB-1)는 Epic 8에서 이미 끝났고, 이 에픽은 그 위에 하이브리드를 얹는다.

## Requirements & Constraints

- 라우팅은 4갈래로 분류되어야 한다: 무관/법적 질의 → 부드러운 거절, 광범위/애매한 질의 → 조건 좁혀 되묻기, 정형 조건 질의 → Text-to-SQL, 정형+의미 혼합 질의 → SQL+벡터 하이브리드.
- 하이브리드는 단일 쿼리(구조조건 WHERE + 유사도 ORDER BY)로 조합한다(RRF 없음). 구조조건을 못 뽑으면 기존 벡터검색으로 폴백해 회귀 없이 처리한다.
- 하이브리드로 생성되는 SQL도 예외 없이 기존 SQL 검증기(sql_guard)를 통과해야 하고 판매완료 매물을 강제로 걸러야 한다 — 판매완료 비노출 규칙이 지키는 지점이 기존 3곳(행 단위 접근제어·SQL 검증기·문서 RAG 필터)에서 하이브리드 벡터 검색까지 4번째로 늘어난다. 앱(프론트) 레벨 필터링은 금지하고 쿼리/DB 레벨에서만 막는다 — 보안 블로커 등급 요구사항이다.
- 가이드 문서(코퍼스)는 검색 조건/가중치로 반영되어야 하지만 답변 문장 자체는 여전히 결정론적(고정 템플릿 조립)으로 생성해야 한다 — LLM이 가이드 본문으로 자유 문장을 만들지 않는다.
- 코사인 거리가 임계값 이하일 때만 가이드 문서를 답변 근거로 채택한다(임계값은 하드코딩이 아니라 실측 질의셋으로 튜닝해 확정).
- 문서 청킹은 현 규모(page-level)에서는 도입하지 않는다 — 문서 20개 이상 또는 문서당 800토큰 이상이 되기 전까지는 조건부 보류.
- LangSmith 트레이싱은 환경변수 2개만으로 켜지는 무료 티어를 쓴다(코드 변경 없음, 평가 자동화·유료 Deployment는 도입 안 함, 월 5000 트레이스 상한).
- `/ai/search`는 로그인(JWT) 필수를 유지한다 — 비로그인 열람 허용은 매물 목록/상세에만 적용되고 AI 검색은 호출마다 Gemini 실비가 드는 "행동"이라 별개다. 이 프로젝트는 "비용이 드는 엔드포인트는 신원을 요구한다"는 원칙을 전 에픽에 걸쳐 유지하며, 하이브리드 도입으로 검색 1회당 LLM+임베딩 호출이 늘어나는 것도 같은 근거로 신원 요구를 완화할 이유가 되지 않는다.
- 되묻기(CLARIFY)는 서버가 세션 상태를 두지 않는(무상태) 방식이다 — 되묻기 문장을 answer로 반환하고, 사용자의 다음 메시지를 클라이언트가 이전 맥락과 이어붙여 재전송한다. 최대 2~3턴까지만 허용하고, 초과하면 현재까지의 조건으로 결과를 강제 제시한다(무한 되묻기 금지).
- 거절(REJECT)은 고정 템플릿만 쓴다 — LLM 자유 재작성 금지. 0건·거절 응답의 다양성도 문구 생성이 아니라 서버가 내려주는 구조화 사유 데이터(`narrowed_by`)를 결정론 템플릿이 조립해서 만든다.
- AI 검색 입력은 서버 측에서도 500자 상한을 검증한다(클라이언트 검증만으로는 우회 가능).
- 검증 게이트는 모두 실측으로 통과해야 한다: G1(되묻기 과다발동 방지 — 명시조건 질의가 CLARIFY로 새면 실패), G2(회귀 — 실측 기준선 이하로 떨어지면 실패, 13.1에서 심고 이후 RAG 스토리마다 재실행), SM-F(기존 AI 검색 시연 3종 유지), SM-G(신규 분기 3종 — 하이브리드·되묻기·거절 각 1개 이상 실동작), CM-B(sql_guard·ai_readonly·판매완료 비노출이 하이브리드/실시간 전환 후에도 유지).
- 하이브리드 경로는 SQL 생성 LLM 호출과 임베딩 호출을 둘 다 태우므로, 기존보다 더 많은 질의가 이 비용 구조를 타게 된다는 점을 설계에서 인지해야 한다(비용 축은 DB 권한 축과 별개 문제 — "안전하다"가 "비용이 안 든다"를 뜻하지 않는다).

## Technical Decisions

- Reuse-first 원칙: 신규 인프라를 만들지 않고 기존 LangGraph StateGraph·sql_guard·ai_readonly·corpus 로더·임베딩 파이프라인 위에 노드만 추가한다. `interrupt()`나 체크포인터 같은 무거운 신규 인프라는 도입하지 않는다.
- 임베딩은 gemini-embedding-001(768차원) 고정, pgvector `vector(768)` 스키마 불변 — 하이브리드로도 이 축은 바뀌지 않는다.
- 벡터절은 LLM이 아니라 코드가 조립한다: `ORDER BY embedding <=> %s::vector LIMIT k`에서 `%s`는 질의 임베딩을 바인드 파라미터로, `LIMIT k`는 코드가 붙이는 정수 리터럴이다(바인드 아님). LLM은 WHERE의 구조조건만 생성한다. sql_guard의 벡터 관련 화이트리스트(`<=>`·`::vector`·`embedding`)는 전역이 아니라 위치 스코프로 넣는다 — 어디에 있든 통과시키면 안전하지 않다.
- 하이브리드 SQL 회귀 테스트는 최소 3케이스가 필요하다: 정상 벡터 쿼리 통과 / OR·서브쿼리 주입 거부 / status 필터 누락 거부.
- 라우팅 4분기는 `RouterDecision` Literal 타입·`_fallback_route`·`_route_decision` 세 곳이 항상 락스텝으로 갱신되어야 한다 — 하나만 빠뜨리면 새 라우트가 조용히 이전 갈래로 흡수되는 회귀가 생긴다.
- AI 응답 계약: `{answer, listings[], route, narrowed_by?, clarify?}`. `narrowed_by`는 저장 단위(원) 그대로의 정규화 술어 배열(예 `["price<=30000000"]`)이며 결정론 템플릿이 문구로 조립한다. `clarify`는 `route='CLARIFY'`일 때만 채워지는 `{question, chips[]}` 구조다. 둘 다 추가 LLM 호출 없이 조립된다.
- 되묻기 상태(멀티턴 맥락)는 클라이언트가 소유하고 sessionStorage에 지속시켜 새로고침에도 살아남게 한다. **상한은 서버가 강제한다** — `api/app/graph/graph.py`의 `_CLARIFY_TURN_CAP`(=3)이 `context` 길이로 총 턴 수를 계산해 `_clarify_step`에서 막고, 초과하면 클라이언트 협조와 무관하게 `doc_rag_node`로 결과를 강제 제시한다. 무상태는 "상태를 저장하지 않는다"는 뜻이지 "판정하지 않는다"가 아니다 — 클라이언트만 세는 상한은 상한이 아니다(web 클라이언트엔 턴 카운터가 없다).
- 커넥션 풀 롤 격리(`BEGIN; SET LOCAL ROLE ai_readonly; ...; COMMIT`, 세션 레벨 SET ROLE 금지)는 Epic 8에서 이미 완료된 전제이며, 이 에픽의 하이브리드 SQL 실행 전체가 그 위에서 돈다.
- LangSmith는 API 쪽 RAG 트레이싱만 담당한다(웹소켓·이미지 업로드 실패 등은 별도 구조화 로그, 이 에픽 범위 밖).

## UX & Interaction Patterns

- 칩은 스타일이 다른 2종이다 — 상시 제안칩(petrol 반투명, 입력바 위 상시 노출)과 맥락 칩(되묻기·거절 전용, 탭 시 petrol 채움 "선택됨" 상태로 전환). 맥락 칩 탭은 자유 타이핑과 항상 동등한 입력 경로이며, 자유 타이핑은 칩 존재와 무관하게 항상 병존한다.
- 거절 응답에는 원 조건으로 되돌아갈 수 있는 재제안 칩을 함께 제시한다(막다른 길로 끝내지 않음).
- 아이콘 전용의 작은 탭 요소(되묻기/제안 칩 포함)는 시각 크기와 무관하게 히트 영역이 44×44px 이상이어야 한다.
- 칩의 "선택됨" 상태는 시각(채움색)뿐 아니라 `aria-pressed` 등 스크린리더용 상태 전달도 함께 갖춰야 한다.

## Cross-Story Dependencies

- 13.1(sql_guard 정비 + 회귀 기준선)이 선행되어야 13.3(하이브리드 검색)이 안전하게 SQL을 생성할 수 있다.
- 13.2(4분기 라우팅 골격)가 있어야 13.3(HYBRID)·13.4(CLARIFY)·13.5(REJECT) 각 갈래가 실제로 호출될 진입점이 생긴다.
- 13.8(exit-gate 검증)은 13.1~13.7 전체가 구현된 뒤에만 의미가 있는 종합 검증 스토리다 — G2 미통과 시 에픽을 종료할 수 없다.
- 13.9(라우팅 안정화)는 13.8의 G2 게이트가 **통과한 뒤에만** 착수한다 — 13.8이 쓴 기준선을 흔들지 않기 위해서다. 13.9가 라우팅 동작을 다시 바꾸므로, 에픽 종료 판정은 13.8만이 아니라 13.9의 재검증 통과까지 필요하다.
- Epic 8에서 이미 만든 DB 커넥션 풀 롤 격리(AC-DB-1)와 ListingCard 응답 계약 셸(image_url·view_count·image_count 등 nullable 필드)이 이 에픽의 전제 조건이다 — 하이브리드 검색 결과 카드도 동일 ListingCard 계약을 그대로 사용한다.
- Epic 11의 상단 내비는 역할 분기 훅 자리로 미리 설계돼 있어, 이 에픽이 나중에 그 구조를 재작성할 필요가 없도록 되어 있다.
