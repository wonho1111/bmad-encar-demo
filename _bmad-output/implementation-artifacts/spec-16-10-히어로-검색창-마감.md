## Intent

**Problem:** 16.9가 히어로의 **구조**(전체폭 밴드·앱바 이음매·배경 장식 존재)는 맞췄지만, 사용자가 실기기로 보고도 "퀄리티가 떨어진다"고 한 원인은 그 위의 **네 가지 마감**이다 — ①헤드라인이 목업 대비 절반 크기(19px)에 eyebrow 라벨이 없고(DW-767) ②검색창에 여전히 테두리가 그려지며(원인 특정됨) ③차 실루엣이 목업 라인아트가 아니라 꽉 찬 Material 아이콘이고 웹 히어로엔 아예 없으며 ④히어로 하단 곡률(22)이 실기기에서 과하게 둥글어 보이고 카드 radius(10)도 웹 토큰(16)과 어긋난다.

**Approach:** 같은 화면의 마감 축이라 한 커밋으로 묶는다(16.9 선례와 동일 이유 — 중간 상태가 어색함). 검색창 테두리는 `InputDecoration.border: InputBorder.none`이 테마의 `enabledBorder`/`focusedBorder`를 덮지 못하는 게 원인이라는 걸 Flutter SDK 소스로 직접 재확인했다(아래 Design Notes) — 그 둘을 이 필드에서만 명시적으로 끈다. 실루엣은 목업의 고정 SVG 경로를 `CustomPainter`로 이식한다(새 패키지 의존성 없이, 앱엔 SVG 렌더 인프라가 없고 이건 정적 도형 하나뿐이라 A2 단순함 원칙상 `flutter_svg`를 새로 들일 근거가 없다) — 같은 자산을 웹 히어로에도 인라인 SVG로 추가한다(웹은 이미 네이티브로 SVG를 쓴다). 헤드라인 크기는 에픽 텍스트의 "30~34px" 인용이 실제로는 데스크톱/태블릿 웹 프레임(`consistency-1.html:541,568`)을 가리킨 오표기였음을 확인했고(진짜 "네이티브 앱" 프레임은 `.app-hero h2`=26px), `DESIGN.md` 스파인의 `typography.scale.display`(36, "히어로 헤드라인"으로 명시)가 목업과 충돌 시 우선한다는 이 프로젝트 자체 규칙과, AC가 요구하는 검사 자체가 절대값이 아니라 **관계**(카드 차량명보다 크다)라는 점에서 36px을 채택한다 — 세 출처 중 스파인이 유일하게 그 자체로 우선순위를 명시한 정본이다.

## Boundaries & Constraints

**Always:**
- 헤드라인(`home_screen.dart:344-354` 부근 `RichText`)을 `fontSize: 36`(`DESIGN.md` `typography.scale.display`)으로, "원하는 차를" / "말로 찾으세요"로 줄바꿈해 2줄로 렌더한다(목업 앱 프레임 마크업 `원하는 차를<br><em>말</em>로 찾으세요`과 동일 지점에서 끊는다). 굵기(800)·"말" amber 강조는 유지.
- 헤드라인 바로 위에 eyebrow 라벨("AI 매물 검색")을 새로 추가한다. 스타일은 `consistency-1.html` `.eyebrow`(반투명 흰 배경 pill·얇은 테두리·작은 점 인디케이터·자간 넓힌 12px, `DESIGN.md` `typography.scale.caption`과 크기 일치)를 따르되 **새 색 토큰을 만들지 않고** 기존 `AppColors`(예: 텍스트·테두리=`onPetrolMuted`, 점 인디케이터=`accentAmber`)로 구성한다 — 정확한 색조는 목업 간에도 갈리므로(consistency-1.html은 teal, app-home-2.html은 amber) 검사도 색을 단언하지 않는다.
- 히어로 검색창(`home_screen.dart:373-381` 부근 `TextField`)의 `InputDecoration`에 `enabledBorder: InputBorder.none`과 `focusedBorder: InputBorder.none`을 **이 필드에서만** 명시적으로 추가한다(기존 `border: InputBorder.none`은 그대로 둬도 무해하지만 이 두 줄이 실제 수정이다). `app_theme.dart`의 전역 `InputDecorationTheme`은 건드리지 않는다(로그인·등록 폼이 함께 쓴다).
- 차 실루엣(`Key('hero_car_silhouette')`, 현재 `Icon(Icons.directions_car_filled, ...)`)을 `CustomPainter`/`Path`로 교체한다. 그리는 도형은 `consistency-1.html`의 `.app-hero .silhouette`(viewBox `0 0 640 220`)와 정확히 같다: `path d="M6,150 C30,120 74,112 122,110 L168,72 C188,54 224,45 276,45 L398,47 C452,49 496,71 528,110 L590,122 C618,128 634,144 634,168 L634,192 L566,192 A42,42 0 0 0 482,192 L246,192 A42,42 0 0 0 162,192 L26,192 C14,192 6,183 6,170 Z"` + 바퀴 원 2개(`cx=204,cy=192,r=30` / `cx=524,cy=192,r=30`). 배치는 같은 목업 규칙(`right:-8%; top:-14%; width:56%; opacity:.09`)을 히어로 밴드 자체 폭/높이 비율로 환산해 적용한다(현재의 고정 픽셀 `top:-6,right:-36,size:150`은 추정값이었다 — 폭이 바뀌어도 같은 비율을 유지하게 한다). `Key('hero_car_silhouette')`는 그대로 유지해 기존 위젯 탐색 경로가 깨지지 않게 한다.
- 같은 실루엣 자산(동일 path 데이터)을 `web/src/components/landing/HeroSearch.tsx`의 `<section>` 안에 인라인 `<svg>` 배경 장식으로 추가한다 — 같은 배치 규칙을 쓰되 웹 변경은 이 배경 요소 하나로 한정한다(로그인 분기·제출 로직·문구·검색 pill 구조는 그대로 둔다). 이 에픽의 Non-goals("웹 랜딩 재작업")는 재작업을 금지하는 것이지, 스파인이 요구한 배경 요소를 넣는 이번 결정(사용자 명시 확정)과 충돌하지 않는다.
- 히어로 하단 곡률을 `home_screen.dart`의 `BorderRadius.only(bottomLeft/bottomRight: Radius.circular(22))` → `16`으로 낮춘다(AC가 지정한 14~16 구간 안이며, 아래 카드 radius와 같은 값이라 두 마감이 서로 어긋나지 않는다).

- 아래 축마다 위젯 테스트를 추가하고, 채택 전 일부러 깨서 red를 확인한 뒤 되돌려 green을 확인한다(CLAUDE.md B4): ①헤드라인의 실효 `fontSize`가 매물 카드 차량명 텍스트의 실효 `fontSize`보다 크다(관계로 단언 — 절대값을 박지 않는다, DW-767이 이미 이 이유를 명시했다) ②eyebrow 위젯이 헤드라인보다 위(먼저 렌더)에 있다 ③히어로 검색창에서 **실제로 그려지는 테두리**가 없다(로컬 `InputDecoration.border` 필드가 아니라 `applyDefaults` 이후의 유효 `enabledBorder`/`focusedBorder`를 확인 — 그 필드만 보면 이미 `InputBorder.none`이라 vacuous해진다) ④`hero_car_silhouette` 위젯이 더 이상 `Icon`이 아니다 ⑤`ListingCard`의 `shape`/사진 클립 radius가 16이다.

**Block If:** 없음 — 위 다섯 축(타이포 수치·색·실루엣 구현 방식·곡률 값·실기기 검증 처리)은 모두 스파인 우선 규칙·기존 팔레트·A2 단순함 원칙·16.9 선례로 이 스펙 안에서 근거와 함께 확정했다.

## Design Notes

**검색창 테두리 원인 — 이 세션이 Flutter SDK 소스로 직접 재확인.** `packages/flutter/lib/src/material/input_decorator.dart`의 `InputDecoration.applyDefaults`(라인 ~4075-4082)는 로컬 `InputDecoration`의 `enabledBorder`/`focusedBorder`가 `null`이면 `InputDecorationTheme`의 값으로 채운다(`enabledBorder ?? theme.enabledBorder`). 이 히어로 `TextField`는 `border: InputBorder.none`만 설정하고 `enabledBorder`/`focusedBorder`는 지정하지 않았으므로, `applyDefaults` 이후 유효 데코레이션엔 테마의 `OutlineInputBorder`(`app_theme.dart:111-121`)가 그대로 들어간다. 그리고 실제 테두리를 고르는 로직(같은 파일 라인 ~2361-2369)은 `enabled`/`focused` 상태에서 `decoration.enabledBorder`/`decoration.focusedBorder`를 **`decoration.border`보다 먼저** 쓴다 — `border: InputBorder.none`은 그 둘이 모두 `null`일 때만 쓰이는 폴백이라 이 경우엔 죽은 코드다. 따라서 로컬 `InputDecoration`에 `enabledBorder: InputBorder.none`·`focusedBorder: InputBorder.none`을 **명시**해야 실제로 사라진다 — 이건 에픽 AC의 진단(`border`가 나머지 둘을 덮지 않는다)이 맞고, 처음 이 스토리를 조사한 서브에이전트가 "`border: InputBorder.none`만으로 충분하다"고 보고한 건 `applyDefaults`의 테마 병합 단계를 놓친 오판이었다 — 이 세션이 SDK 소스로 재검증해 정정했다.

**헤드라인 36px의 근거 — 에픽 텍스트의 "30~34px" 인용은 실제로 오표기였다.** `deferred-work.md` DW-767과 에픽 AC 둘 다 "목업 앱 프레임 기준 30~34px"의 근거로 `consistency-1.html:541`(34px)·`:568`(30px)을 든다. 그러나 그 두 줄은 각각 "데스크톱 1280px"(라인 529 `frame-cap`)과 "태블릿 834px"(라인 558)절 안에 있는 **웹 프레임**이다. 진짜 "네이티브 앱(Flutter)" 폰 목업(같은 파일, "MOBILE 390" 섹션 옆의 `phone-col`)의 헤드라인은 `.app-hero h2`(CSS 라인 314) = **26px**이다 — 즉 에픽이 인용한 숫자도, 진짜 앱 프레임 목업도 스파인의 `typography.scale.display`(36, "히어로 헤드라인"으로 명시, 32~40 유동)와 다르다. `DESIGN.md`는 스스로 "스파인이 목업과 충돌하면 스파인이 우선한다"고 못박고 있고, 이 스토리의 검사 자체도 절대값이 아니라 **관계**(카드 차량명보다 크다)만 요구하므로, 세 숫자 중 유일하게 그 자체로 우선순위를 주장하는 스파인 값(36)을 채택한다. 30~34나 26을 썼어도 관계 검사는 통과하지만, 스파인이 명시적으로 우선한다고 선언한 값을 두고 오표기된 인용을 따를 이유가 없다.

**곡률·radius 값 — 22 그대로 유지하지 않는 이유.** `app-home-2.html`의 `.ai-hero` radius는 22px로 현재 앱 값과 일치하지만, 사용자가 실기기 육안으로 "곡선이 과하다"고 판단해 14~16으로 낮추라고 명시했다(목업 수치보다 사용자의 실기기 판단이 이 축에서 우선). 16을 골라 카드 radius(웹 토큰과 맞추며 함께 16으로 올리는 값)와 통일했다 — 두 마감 요소가 같은 값을 쓰면 나중에 리팩터가 "왜 다른가"를 다시 묻지 않는다.
